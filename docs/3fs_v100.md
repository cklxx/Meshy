# 3FS 单机部署（V100 节点 10.37.2.27）

单台 1×V100 / 8 CPU / 31 GB RAM / 无 RDMA 网卡的机器上，用 soft-RoCE +
容器跑通一套完整的 [deepseek-ai/3FS](https://github.com/deepseek-ai/3FS)
（commit `22fca045`，2026-05-07）：FoundationDB、mgmtd、meta、两个 storage
服务（RF=2）、FUSE 客户端，挂载在 `/3fs/stage`。本文记录部署步骤、资源裁剪、
冒烟结果，以及 SGLang HiCache / TransferQueue / checkpoint 三处只读调研结论。

部署脚本在 `deploy/3fs-v100/`。

## 1. 拓扑

| 角色 | 实例 | 端口（RDMA / TCP） | 数据目录 |
|---|---|---|---|
| FoundationDB 7.3.63 | 1 | 4500 | 容器内 `/opt/3fs/fdb` |
| mgmtd（node 1） | 1 | 8000 / 9000 | FDB |
| meta（node 100） | 1 | 8001 / 9001 | FDB |
| storage s1（node 10001） | 1 | 8002 / 9002 | `/data00/meshy/fs3/run/data-s1` |
| storage s2（node 10002） | 1 | 8003 / 9003 | `/data00/meshy/fs3/run/data-s2` |
| FUSE | 1 | — | 挂载 `/3fs/stage` |

- **soft-RoCE**：`rdma_rxe` 模块在 `eth0` 上建 `rxe0`，3FS 的 RDMA 传输走它。
  同机回环实测 ib_write_bw ≈ 912 MB/s（soft-RoCE 软件实现，仅供功能打通，
  非性能目标）。
- **单机两个 storage 服务**：3FS 的 CRAQ 副本链要求至少 2 个存储成员；上游
  FAQ 明确单机测试可在一台机器上起多个 storage 服务。两个实例必须有不同的
  node id、监听端口和 target 目录，因此各自使用一份完整本地配置，不能共用
  mgmtd 下发的一份 STORAGE 模板。
- **全部服务在一个 privileged 容器里**：host 网络（直接看到 `rxe0` 和
  10.37.2.27）、`/dev/fuse` + `/dev/infiniband` 透传、FUSE 挂载点以 rshared
  传播到宿主。这样所有 3FS 二进制共享 builder 镜像里的 folly/libfuse3/FDB
  client/ibverbs 运行库，不污染宿主。

## 2. soft-RoCE

```bash
sudo modprobe rdma_rxe
sudo rdma link add rxe0 type rxe netdev eth0
rdma link show rxe0          # state ACTIVE
ibv_devices                  # rxe0
```

脚本：`00_setup_rxe.sh`。`rdma link add` 非持久（重启需重跑）；脚本幂等。
验证回环：

```bash
sudo ib_write_bw -d rxe0 -F -D 1 &
sudo ib_write_bw -d rxe0 -F -D 1 10.37.2.27
# 65536 B: BW average ≈ 912 MB/s
```

## 3. 编译

容器内编译，用上游 `dockerfile/dev.dockerfile`（Ubuntu 22.04 + clang-14 +
FDB client 7.3.63 + libfuse 3.16.2，已含 ibverbs 和 librxe provider）。
编译需要访问外网，容器构建/运行都用 `--network=host` 并注入公司代理。

```bash
# 在 /data00/meshy/fs3 下
git clone https://github.com/deepseek-ai/3FS
cd 3FS && git submodule update --init --recursive --depth 1 && ./patches/apply.sh

# 1) builder 镜像  2) 只编译需要的 5 个二进制
bash deploy/3fs-v100/10_build.sh builder
bash deploy/3fs-v100/10_build.sh compile
# build/bin/{mgmtd_main,meta_main,storage_main,hf3fs_fuse_main,admin_cli}
```

两点上游坑（脚本已规避）：

- `apache-arrow-cpp`（analytics 组件用）编译时从 GitHub clone，代理下仍可能
  超时；mgmtd/meta/storage/fuse/admin_cli 不依赖它，用 `--target` 只编这 5 个。
- 浅克隆没有 git tag，`cmake/GitVersion.cmake` 在 `git-state.txt` 为空时
  `if()` 展开报错。补丁：`if (NOT DEFINED GIT_HASH_CACHE OR GIT_HASH_CACHE
  STREQUAL "")`，并删除残留的空 `build/git-state.txt`。`-DSHUFFLE_METHOD
  =g++11` 按上游 README 固定 shuffle 算法。

## 4. 配置

`gen_configs.py` 从 stock `configs/*.toml` 生成单机配置，只改必须改的键。

最重要的是**内存裁剪**。stock storage 配置按胖节点（16 NVMe、百 GB 内存）
标定，单个 storage 服务的硬开销就有：

- RDMA buffer pool：`rdmabuf_count=1024 × 4MB + big_rdmabuf_count=64 ×
  64MB = 8 GB`；
- LevelDB / RocksDB block cache：各 `8 GB`。

一台 31 GB 机器跑两个实例会被直接打爆。裁剪为每实例：

```toml
rdmabuf_count = 16                 # 16×4MB = 64MB
big_rdmabuf_count = 4              # 4×64MB = 256MB
leveldb_block_cache_size = '64MB'
rocksdb_block_cache_size = '64MB'
leveldb_write_buffer_size = '4MB'
rocksdb_write_buffer_size = '4MB'
```

其余裁剪：aio/write worker `num_threads 32→2`、`num_channels 1024→64`、
`ioengine=libaio`（关 io_uring）、chunk meta-store `allocate_size
256MB→64MB`、关 event trace、不部署 monitor_collector/ClickHouse
（`remote_ip=""`）。两个实例分别设监听端口 8002/9002 与 8003/9003、
target 路径 `.../data-s1`、`.../data-s2`，并 `allow_disk_without_uuid=true`
（两个目录在同一根文件系统上，没有独立磁盘 UUID）。

## 5. 启动

```bash
bash deploy/3fs-v100/10_build.sh runtime     # 3fs:dev 运行镜像
bash deploy/3fs-v100/30_container.sh init    # 生成配置、建目录
bash deploy/3fs-v100/30_container.sh run     # 起容器并引导集群
```

实测中遇到并已在脚本/镜像里处理的坑：

- **FDB cluster key 必须十六进制**：`description:key@host:port` 里 key 含
  下划线（如 `3fs_local`）会被 fdbcli 以 “Connection string invalid”
  拒绝；用 `3f510ca1`。
- **fdbmonitor 托管的 fdbserver 不监听**：容器内经 fdbmonitor 拉起的
  fdbserver 绑定到容器主机名地址、4500 无监听；脚本改为直接以
  `-p 127.0.0.1:4500` 启动单个 fdbserver（单机足够）。
- **hostname 只解析到 IPv6**：宿主机名经公司 DNS 只有 AAAA 记录，导致
  storage 向 mgmtd 上报空 IPv4 routing 地址，client 连 `TCP://0.0.0.0:0`。
  引导前在容器 `/etc/hosts` 把主机名钉到 10.37.2.27，且必须在 storage
  启动前完成（改完要重启 storage 才会重新上报）。
- **libjemalloc.so.2 缺失**：二进制动态链接自建 jemalloc，运行镜像额外
  装 `libjemalloc2`。
- **admin_cli 数组参数要带引号**：CLI 覆盖 TOML 数组时值必须是
  `--config.x.y '["RDMA://10.37.2.27:8000"]'`（元素带引号），否则
  TOML 解析失败。
- **新建文件需要 ≥16 条 chain**：init 时 strip size=16，文件创建会一次
  申请 16 条 chain；只有 1 条链会报
  `InvalidFileLayout ... allocate 16 chains ... found 1`。
  `provision_targets.sh` 因此在每个节点建 16 个 target（同一块盘，
  target index 0..15）并组成 16 条 RF=2 链，而不是上游的 1 条。

容器内 `20_start_cluster.sh` 的引导顺序：

1. 起单进程 FoundationDB，`configure new single ssd`；
2. mgmtd 启动前 `admin_cli init-cluster --mgmtd ... 1 1048576 16`
   （chain table 1，chunk 1 MiB，stripe 16），直接写 FDB；
3. 起 mgmtd，`user-add --root --admin 0 root` 拿 admin token；
4. 起 meta、两个 storage，等两个 node 都在 `list-nodes` 注册；
5. `provision_targets.sh` 在每个节点建 16 个 target（同一块盘，target
   index 0..15），组成 16 条 RF=2 链并上传 chain table；
6. 起 FUSE，挂 `/3fs/stage`，并建一个可写子目录 `/3fs/stage/data`。

target/chain id 按上游 `gen_chain_table.py` 的公式手算（target prefix 1、
chain prefix 9、disk_index 0，target index 0..15）：

```
target(10001,i)=101000100100+i+1   target(10002,i)=101000200100+i+1
chain(i)=900100000+i+1   （i = 0..15，链 = [target(10001,i), target(10002,i)]）
```

集群信息用 `admin_cli ... list-nodes / list-chains / list-chain-tables`
确认。

## 6. 冒烟结果

`40_smoke.sh`（在宿主 `/3fs/stage/data` 上跑）实测：

- **数据一致性**：100 MB 随机数据写入 → 复制 → 重新读取，sha256 一致
  （`INTEGRITY_OK`）；100 个小文件写入并回读正常。
- **顺序带宽**（dd，1 MiB 块，256 MiB，soft-RoCE 同机回环）：
  - 写（`conv=fdatasync`，RF=2 双副本）：**≈ 93 MB/s**
  - 读：**≈ 202 MB/s**

  这是软 RDMA + FUSE 单机回环的功能级数字，不代表 3FS 真实性能；
  ib_write_bw 测得 rxe0 回环上限约 912 MB/s。

**常驻资源**（`docker stats` + `ps`，全部服务在线空闲）：

| 进程 | RSS |
|---|---|
| storage_main ×2 | 各 ≈ 1.4 GB |
| meta_main | ≈ 464 MB |
| hf3fs_fuse_main | ≈ 402 MB |
| mgmtd_main | ≈ 260 MB |
| fdbserver | ≈ 90 MB |
| **容器合计** | **≈ 3.6 GB**（预算 ≤6 GB，达标） |

磁盘：两个 storage target 目录各 ≈ 9.3 GB（chunk engine 按块预分配，
非稀疏），FDB ≈ 0.2 GB，合计 **≈ 19 GB**（预算 ≤100 GB，达标）。
真实写入量很小，预分配占用随配置的 chunk 块大小变化。

## 7. 只读调研（未接入）

### 7.1 SGLang HiCache 的 hf3fs 后端

SGLang 的分层 KV cache（HiCache，L1=GPU、L2=host DRAM、L3=外部存储）内置
名为 **`hf3fs`** 的 L3 后端（`sglang/srt/mem_cache/storage/hf3fs/`）。

- 启用：`--enable-hierarchical-cache --hicache-storage-backend hf3fs`
  （当前主线拼法是 `--hicache-*`，不是旧文档里的 `--hi-cache-*`）。
- 它**不是通过 FUSE 路径写缓存**，而是依赖 hf3fs 的 **usrbio** Python 库
  （`hf3fs-py-usrbio`，或从 novitalabs/3FS fork 编 wheel），以
  `SGLANG_HICACHE_HF3FS_CONFIG_PATH` 指向一个 JSON：
  ```json
  {
    "file_path_prefix": "/3fs/stage/hicache/hicache",
    "file_size": 1099511627776,
    "numjobs": 16,
    "entries": 8
  }
  ```
  后端在该前缀下为每个 rank 打开一个大预分配文件（`.{rank}.bin`），按页
  做 direct IO；多节点共享时再加 `metadata_server_url`（SGLang 自带的
  `mini_3fs_metadata_server`，与 3FS 自身 mgmtd 无关）。
- 推荐搭配（上游示例）：`--page-size 64 --hicache-ratio 2 --hicache-size 0
  --hicache-write-policy write_through --hicache-mem-layout page_first_direct
  --hicache-io-backend direct --hicache-storage-prefetch-policy wait_complete`。

对本项目的含义：要接 HiCache，除了 FUSE 客户端还需要在 SGLang 环境里装
usrbio wheel（需要和 3FS 同工具链编译，是另一项工作）；缓存文件可以落在
本次部署的 `/3fs/stage` 里。单机 soft-RoCE 上 L3 带宽约数百 MB/s 量级，
仅能做功能验证，不是生产缓存层。

### 7.2 TransferQueue 0.1.9 能否挂 3FS

不能直接挂。0.1.9（2026-07-12 的 wheel，`transfer_queue/`）的可插拔存储后端
只有四种：`SimpleStorage`（ZMQ 内存）、`MooncakeStore`、`Yuanrong`、
`Ray`（`storage/{clients,managers,bootstrap}` + `config.yaml` 的
`backend.storage_backend`）。没有 3FS/hf3fs/fs 后端。

唯一与文件系统相关的是 `SimpleStorage` 的 checkpoint：它把整个 storage
unit 用 pickle 直接 `open(path,'wb')` 存到调用方给的路径，代码注释明确
要求多节点时该路径在共享文件系统上。因此 3FS 在这里只能作为**普通共享
文件系统**承接 pickle checkpoint 路径（经 FUSE 挂载即可，无需 TQ 改动），
而不是一个传输/数据面后端。

### 7.3 checkpoint 落 3FS

Meshy 的模型 checkpoint 走 HF 格式的文件路径：`TitanEngine.save_checkpoint`
→ `trainer.save_hf_checkpoint(path)`（`meshy/engine/titan.py`），
`path` 来自 `runtime.checkpoint_path(name, version)`，根目录是
`config.py` 的 `dump_folder`（默认 `./outputs`）。底层是普通文件写入，
没有对象存储/专用后端耦合。

落 3FS 的方式：把 `dump_folder`（或 checkpoint 根路径）指到 FUSE 挂载点
下（如 `/3fs/stage/meshy/ckpt`）即可，训练侧零改动；多节点/多服务也能通过
同一挂载点看到同一份 checkpoint。TransferQueue 的 storage-unit
checkpoint 同理给一个 `/3fs/stage/...` 路径即可。
