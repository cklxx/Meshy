# 3FS 单机部署（V100 节点 10.37.2.27）

单台 1×V100 / 8 CPU / 31 GB RAM / 无 RDMA 网卡的机器上，用 soft-RoCE +
容器跑通一套完整的 [deepseek-ai/3FS](https://github.com/deepseek-ai/3FS)
（commit `22fca045`，2026-05-07）：FoundationDB、mgmtd、meta、两个 storage
服务（RF=2）、FUSE 客户端，挂载在 `/3fs/stage`。本文记录部署步骤、资源裁剪、
冒烟结果，以及 SGLang HiCache / TransferQueue / checkpoint 三处只读调研结论。

部署脚本在 `deploy/3fs-v100/`。

## 1. 拓扑

| 角色 | 实例 | 端口（RDMA / TCP） | 数据目录 |
|---|---|---|---|
| FoundationDB 7.3.63 | 1 | 4500 | 容器内 `/opt/3fs/fdb` |
| mgmtd（node 1） | 1 | 8000 / 9000 | FDB |
| meta（node 100） | 1 | 8001 / 9001 | FDB |
| storage s1（node 10001） | 1 | 8002 / 9002 | `/data00/meshy/fs3/run/data-s1` |
| storage s2（node 10002） | 1 | 8003 / 9003 | `/data00/meshy/fs3/run/data-s2` |
| FUSE | 1 | — | 挂载 `/3fs/stage` |

- **soft-RoCE**：`rdma_rxe` 模块在 `eth0` 上建 `rxe0`，3FS 的 RDMA 传输走它。
  同机回环实测 ib_write_bw ≈ 912 MB/s（soft-RoCE 软件实现，仅供功能打通，
  非性能目标）。
- **单机两个 storage 服务**：3FS 的 CRAQ 副本链要求至少 2 个存储成员；上游
  FAQ 明确单机测试可在一台机器上起多个 storage 服务。两个实例必须有不同的
  node id、监听端口和 target 目录，因此各自使用一份完整本地配置，不能共用
  mgmtd 下发的一份 STORAGE 模板。
- **全部服务在一个 privileged 容器里**：host 网络（直接看到 `rxe0` 和
  10.37.2.27）、`/dev/fuse` + `/dev/infiniband` 透传、FUSE 挂载点以 rshared
  传播到宿主。这样所有 3FS 二进制共享 builder 镜像里的 folly/libfuse3/FDB
  client/ibverbs 运行库，不污染宿主。

## 2. soft-RoCE

```bash
sudo modprobe rdma_rxe
sudo rdma link add rxe0 type rxe netdev eth0
rdma link show rxe0          # state ACTIVE
ibv_devices                  # rxe0
```

脚本：`00_setup_rxe.sh`。`rdma link add` 非持久（重启需重跑）；脚本幂等。
验证回环：

```bash
sudo ib_write_bw -d rxe0 -F -D 1 &
sudo ib_write_bw -d rxe0 -F -D 1 10.37.2.27
# 65536 B: BW average ≈ 912 MB/s
```

## 3. 编译

容器内编译，用上游 `dockerfile/dev.dockerfile`（Ubuntu 22.04 + clang-14 +
FDB client 7.3.63 + libfuse 3.16.2，已含 ibverbs 和 librxe provider）。
编译需要访问外网，容器构建/运行都用 `--network=host` 并注入公司代理。

```bash
# 在 /data00/meshy/fs3 下
git clone https://github.com/deepseek-ai/3FS
cd 3FS && git submodule update --init --recursive --depth 1 && ./patches/apply.sh

# 1) builder 镜像  2) 只编译需要的 5 个二进制
bash deploy/3fs-v100/10_build.sh builder
bash deploy/3fs-v100/10_build.sh compile
# build/bin/{mgmtd_main,meta_main,storage_main,hf3fs_fuse_main,admin_cli}
```

两点上游坑（脚本已规避）：

- `apache-arrow-cpp`（analytics 组件用）编译时从 GitHub clone，代理下仍可能
  超时；mgmtd/meta/storage/fuse/admin_cli 不依赖它，用 `--target` 只编这 5 个。
- 浅克隆没有 git tag，`cmake/GitVersion.cmake` 在 `git-state.txt` 为空时
  `if()` 展开报错。补丁：`if (NOT DEFINED GIT_HASH_CACHE OR GIT_HASH_CACHE
  STREQUAL "")`，并删除残留的空 `build/git-state.txt`。`-DSHUFFLE_METHOD
  =g++11` 按上游 README 固定 shuffle 算法。

## 4. 配置

`gen_configs.py` 从 stock `configs/*.toml` 生成单机配置，只改必须改的键。

最重要的是**内存裁剪**。stock storage 配置按胖节点（16 NVMe、百 GB 内存）
标定，单个 storage 服务的硬开销就有：

- RDMA buffer pool：`rdmabuf_count=1024 × 4MB + big_rdmabuf_count=64 ×
  64MB = 8 GB`；
- LevelDB / RocksDB block cache：各 `8 GB`。

一台 31 GB 机器跑两个实例会被直接打爆。裁剪为每实例：

```toml
rdmabuf_count = 16                 # 16×4MB = 64MB
big_rdmabuf_count = 4              # 4×64MB = 256MB
leveldb_block_cache_size = '64MB'
rocksdb_block_cache_size = '64MB'
leveldb_write_buffer_size = '4MB'
rocksdb_write_buffer_size = '4MB'
```

其余裁剪：aio/write worker `num_threads 32→2`、`num_channels 1024→64`、
`ioengine=libaio`（关 io_uring）、chunk meta-store `allocate_size
256MB→64MB`、关 event trace、不部署 monitor_collector/ClickHouse
（`remote_ip=""`）。两个实例分别设监听端口 8002/9002 与 8003/9003、
target 路径 `.../data-s1`、`.../data-s2`，并 `allow_disk_without_uuid=true`
（两个目录在同一根文件系统上，没有独立磁盘 UUID）。

## 5. 启动

```bash
bash deploy/3fs-v100/10_build.sh runtime     # 3fs:dev 运行镜像
bash deploy/3fs-v100/30_container.sh init    # 生成配置、建目录
bash deploy/3fs-v100/30_container.sh run     # 起容器并引导集群
```

实测中遇到并已在脚本/镜像里处理的坑：

- **FDB cluster key 必须十六进制**：`description:key@host:port` 里 key 含
  下划线（如 `3fs_local`）会被 fdbcli 以 “Connection string invalid”
  拒绝；用 `3f510ca1`。
- **fdbmonitor 托管的 fdbserver 不监听**：容器内经 fdbmonitor 拉起的
  fdbserver 绑定到容器主机名地址、4500 无监听；脚本改为直接以
  `-p 127.0.0.1:4500` 启动单个 fdbserver（单机足够）。
- **hostname 只解析到 IPv6**：宿主机名经公司 DNS 只有 AAAA 记录，导致
  storage 向 mgmtd 上报空 IPv4 routing 地址，client 连 `TCP://0.0.0.0:0`。
  引导前在容器 `/etc/hosts` 把主机名钉到 10.37.2.27，且必须在 storage
  启动前完成（改完要重启 storage 才会重新上报）。
- **libjemalloc.so.2 缺失**：二进制动态链接自建 jemalloc，运行镜像额外
  装 `libjemalloc2`。
- **admin_cli 数组参数要带引号**：CLI 覆盖 TOML 数组时值必须是
  `--config.x.y '["RDMA://10.37.2.27:8000"]'`（元素带引号），否则
  TOML 解析失败。
- **新建文件需要 ≥16 条 chain**：init 时 strip size=16，文件创建会一次
  申请 16 条 chain；只有 1 条链会报
  `InvalidFileLayout ... allocate 16 chains ... found 1`。
  `provision_targets.sh` 因此在每个节点建 16 个 target（同一块盘，
  target index 0..15）并组成 16 条 RF=2 链，而不是上游的 1 条。

容器内 `20_start_cluster.sh` 的引导顺序：

1. 起单进程 FoundationDB，`configure new single ssd`；
2. mgmtd 启动前 `admin_cli init-cluster --mgmtd ... 1 1048576 16`
   （chain table 1，chunk 1 MiB，stripe 16），直接写 FDB；
3. 起 mgmtd，`user-add --root --admin 0 root` 拿 admin token；
4. 起 meta、两个 storage，等两个 node 都在 `list-nodes` 注册；
5. `provision_targets.sh` 在每个节点建 16 个 target（同一块盘，target
   index 0..15），组成 16 条 RF=2 链并上传 chain table；
6. 起 FUSE，挂 `/3fs/stage`，并建一个可写子目录 `/3fs/stage/data`。

target/chain id 按上游 `gen_chain_table.py` 的公式手算（target prefix 1、
chain prefix 9、disk_index 0，target index 0..15）：

```
target(10001,i)=101000100100+i+1   target(10002,i)=101000200100+i+1
chain(i)=900100000+i+1   （i = 0..15，链 = [target(10001,i), target(10002,i)]）
```

集群信息用 `admin_cli ... list-nodes / list-chains / list-chain-tables`
确认。

## 6. 冒烟结果

`40_smoke.sh`（在宿主 `/3fs/stage/data` 上跑）实测：

- **数据一致性**：100 MB 随机数据写入 → 复制 → 重新读取，sha256 一致
  （`INTEGRITY_OK`）；100 个小文件写入并回读正常。
- **顺序带宽**（dd，1 MiB 块，256 MiB，soft-RoCE 同机回环）：
  - 写（`conv=fdatasync`，RF=2 双副本）：**≈ 93 MB/s**
  - 读：**≈ 202 MB/s**

  这是软 RDMA + FUSE 单机回环的功能级数字，不代表 3FS 真实性能；
  ib_write_bw 测得 rxe0 回环上限约 912 MB/s。

**常驻资源**（`docker stats` + `ps`，全部服务在线空闲）：

| 进程 | RSS |
|---|---|
| storage_main ×2 | 各 ≈ 1.4 GB |
| meta_main | ≈ 464 MB |
| hf3fs_fuse_main | ≈ 402 MB |
| mgmtd_main | ≈ 260 MB |
| fdbserver | ≈ 90 MB |
| **容器合计** | **≈ 3.6 GB**（预算 ≤6 GB，达标） |

磁盘：两个 storage target 目录各 ≈ 9.3 GB（chunk engine 按块预分配，
非稀疏），FDB ≈ 0.2 GB，合计 **≈ 19 GB**（预算 ≤100 GB，达标）。
真实写入量很小，预分配占用随配置的 chunk 块大小变化。

## 7. 只读调研（未接入）

### 7.1 SGLang HiCache 的 hf3fs 后端

SGLang 的分层 KV cache（HiCache，L1=GPU、L2=host DRAM、L3=外部存储）内置
名为 **`hf3fs`** 的 L3 后端（`sglang/srt/mem_cache/storage/hf3fs/`）。

- 启用：`--enable-hierarchical-cache --hicache-storage-backend hf3fs`
  （当前主线拼法是 `--hicache-*`，不是旧文档里的 `--hi-cache-*`）。
- 它**不是通过 FUSE 路径写缓存**，而是依赖 hf3fs 的 **usrbio** Python 库
  （`hf3fs-py-usrbio`，或从 novitalabs/3FS fork 编 wheel），以
  `SGLANG_HICACHE_HF3FS_CONFIG_PATH` 指向一个 JSON：
  ```json
  {
    "file_path_prefix": "/3fs/stage/hicache/hicache",
    "file_size": 1099511627776,
    "numjobs": 16,
    "entries": 8
  }
  ```
  后端在该前缀下为每个 rank 打开一个大预分配文件（`.{rank}.bin`），按页
  做 direct IO；多节点共享时再加 `metadata_server_url`（SGLang 自带的
  `mini_3fs_metadata_server`，与 3FS 自身 mgmtd 无关）。
- 推荐搭配（上游示例）：`--page-size 64 --hicache-ratio 2 --hicache-size 0
  --hicache-write-policy write_through --hicache-mem-layout page_first_direct
  --hicache-io-backend direct --hicache-storage-prefetch-policy wait_complete`。

对本项目的含义：要接 HiCache，除了 FUSE 客户端还需要在 SGLang 环境里装
usrbio wheel（需要和 3FS 同工具链编译，是另一项工作）；缓存文件可以落在
本次部署的 `/3fs/stage` 里。单机 soft-RoCE 上 L3 带宽约数百 MB/s 量级，
仅能做功能验证，不是生产缓存层。

### 7.2 TransferQueue 0.1.9 能否挂 3FS

不能直接挂。0.1.9（2026-07-12 的 wheel，`transfer_queue/`）的可插拔存储后端
只有四种：`SimpleStorage`（ZMQ 内存）、`MooncakeStore`、`Yuanrong`、
`Ray`（`storage/{clients,managers,bootstrap}` + `config.yaml` 的
`backend.storage_backend`）。没有 3FS/hf3fs/fs 后端。

唯一与文件系统相关的是 `SimpleStorage` 的 checkpoint：它把整个 storage
unit 用 pickle 直接 `open(path,'wb')` 存到调用方给的路径，代码注释明确
要求多节点时该路径在共享文件系统上。因此 3FS 在这里只能作为**普通共享
文件系统**承接 pickle checkpoint 路径（经 FUSE 挂载即可，无需 TQ 改动），
而不是一个传输/数据面后端。

### 7.3 checkpoint 落 3FS

Meshy 的模型 checkpoint 走 HF 格式的文件路径：`TitanEngine.save_checkpoint`
→ `trainer.save_hf_checkpoint(path)`（`meshy/engine/titan.py`），
`path` 来自 `runtime.checkpoint_path(name, version)`，根目录是
`config.py` 的 `dump_folder`（默认 `./outputs`）。底层是普通文件写入，
没有对象存储/专用后端耦合。

落 3FS 的方式：把 `dump_folder`（或 checkpoint 根路径）指到 FUSE 挂载点
下（如 `/3fs/stage/meshy/ckpt`）即可，训练侧零改动；多节点/多服务也能通过
同一挂载点看到同一份 checkpoint。TransferQueue 的 storage-unit
checkpoint 同理给一个 `/3fs/stage/...` 路径即可。

## 8. 接入 Meshy 与 SGLang（T5a）

### 8.1 Meshy 可写目录

挂载根 `/3fs/stage` 是 root:root 0755（3FS 拒绝在根上 chmod），普通训练
用户写不进去。`20_start_cluster.sh` 现在固定建：

```
/3fs/stage/meshy/{kvcache,ckpt,rollout}   属主 uid 1001:1001
```

uid/gid 用 `MESHY_UID`/`MESHY_GID` 覆盖。`chenkailun.c`（uid 1001）在宿主
直接写这些目录验证通过。

### 8.2 usrbio Python 绑定（SGLang hf3fs 后端）

SGLang 的 hf3fs L3 后端 `import hf3fs_fuse.io`，它是 3FS `setup.py` 打出来的
`hf3fs_py_usrbio` wheel（usrbio io_uring，不经 FUSE 读写）。构建/安装：

- `10_build.sh usrbio`：builder 镜像只有 python 3.10，脚本 bind-mount 进 uv
  自管的 CPython 3.12（即共享 venv 用的那个，含 dev 头），在容器内建临时
  venv 打 `hf3fs_py_usrbio-*-cp312-*.whl`，必须带
  `CMAKE_ARGS=-DSHUFFLE_METHOD=g++11`（setup.py 不默认传）。产物在
  `3FS/dist/`。
- `50_install_usrbio.sh`：用 uv pip 装进 `/data00/meshy/venv`。wheel 自带
  `libhf3fs_api_shared.so`，但还动态链接宿主 veLinux 没有的三个 Ubuntu 库
  （`libdouble-conversion.so.3`/`libglog.so.0`/`libdwarf.so.1`），脚本从
  3fs 运行容器拷进 venv 的 site-packages。
- 扩展的 RUNPATH 指向构建容器路径，运行时要把 site-packages 放进
  `LD_LIBRARY_PATH`。固化在 `/data00/meshy/hf3fs_usrbio.env`：
  ```sh
  source /data00/meshy/hf3fs_usrbio.env
  # 等价于 export LD_LIBRARY_PATH=<venv site-packages>:$LD_LIBRARY_PATH
  #         export SGLANG_HICACHE_HF3FS_CONFIG_PATH=/data00/meshy/fs3/hicache_hf3fs_config.json
  ```
  不 source 也能 `import torch`，只有用 hf3fs 后端时需要它。

### 8.3 配置 JSON 与 put/get 校验

`hicache_hf3fs_config.json`（放在 `/data00/meshy/fs3/`）：

```json
{
  "file_path_prefix": "/3fs/stage/meshy/kvcache/hicache",
  "file_size": 1073741824, "numjobs": 1, "entries": 64
}
```

`usrbio_probe.py` 只 import `hf3fs_fuse.io` + `torch`（复刻
`Hf3fsUsrBioClient` 的 ioring/shm 逻辑），**不 import sglang、不依赖
sgl_kernel**，绕开了当前 `libnvrtc.so.13` 缺失导致 sglang 整体不可导入的
问题。它在 `<prefix>.0.bin` 上做确定性字节 put/get、sha256 校验并报带宽。

实测（256 MiB，64 KiB/page，entries=64，rxe 单机回环，宿主 venv）：

```
sha write == sha read   INTEGRITY_OK
usrbio put BW ≈ 10.5 MiB/s
usrbio get BW ≈ 243   MiB/s
```

读与 FUSE 路径（dd ≈202 MB/s）同量级；写慢是 soft-RoCE + 逐 64 KiB 同步
usrbio op 在单 ioring 下的表现（entries 调到 4096 一次性压 256 MiB 会在
rxe 上拿不到完成、超时），属软 RDMA 单机功能级结果，真实网卡会不同。
SGLang HiCache 实际启用仍需其主包可 import（env 在处理 nvrtc），届时加
`--enable-hierarchical-cache --hicache-storage-backend hf3fs` 即可。

### 8.4 recipe 落盘路径

`recipe/grpo_gsm8k_v100.py`（已合入 v100/kern 的 RL 改动）新增三个环境变量，
默认指向 3FS：

| 变量 | 默认 | 作用 |
|---|---|---|
| `XRL_STORAGE_ROOT` | `/3fs/stage/meshy` | Meshy 在 3FS 上的根 |
| `XRL_CKPT_DIR` | `$ROOT/ckpt` | trainer `dump_folder`（HF checkpoint）|
| `XRL_ROLLOUT_DIR` | `$ROOT/rollout` | runtime 根：weights + rollout trajectories |

## 9. usrbio 写带宽定位（T5b）

T5a 的 put ≈10.5 MiB/s 是用 **64 KiB 固定 page + 单 client 串行**测的，
不是 SGLang 的真实 op 大小。两个基准（`micro_op.py` 单 ring 变 op 大小；
`bench_hicache.py` 复刻 SGLang 的 numjobs×entries 并发模型）定位如下。

### 9.1 瓶颈是「每 op 固定 RTT」，不是存储/副本带宽

单 ioring、每 op 一次 submit→wait，128 MiB：

| op 大小 | op 数 | 写 MiB/s | 读 MiB/s |
|---:|---:|---:|---:|
| 64 KiB | 2048 | **10.3** | 55 |
| 256 KiB | 512 | 11.7 | 161 |
| 512 KiB | 256 | 22.4 | 181 |
| 1 MiB | 128 | **86.6** | 181 |
| 2 MiB | 64 | 86.5 | 182 |
| 4 MiB | 32 | 87.0 | 180 |
| 8 MiB | 8 | 130 | 178 |

写带宽随单 op 字节数线性爬升，到 ~1 MiB/op 即达 **85–90 MiB/s**（FUSE 顺序
写水平），再大到 130。说明软 RDMA 回环下每次 usrbio 提交有一个固定往返
开销，64 KiB 小 op 把时间全花在 RTT 上；存储端（chunk 1 MiB、RF=2）本身
不是瓶颈。FUSE 顺序写（dd）93 MiB/s 也与之吻合。

### 9.2 多 client 并发在 rxe 上不可行（真实网卡不会）

`bench_hicache.py` 起 numjobs>1 个独立 ioring（SGLang 默认 numjobs=16）时，
soft-RoCE 单设备的 SQ/CQE 直接报错：`EAGAIN (errno 11)`、`OSError 5`、
`no more sqes when args are added`、`same cqe ... fetched more than once`。
即多个 ioring 抢一个 rxe 队列撑不住；这是软 RDMA 单机的限制，物理 RDMA
网卡每个 QP 有独立硬件队列，numjobs 并发才是 SGLang 生产提速的来源。

### 9.3 关键：SGLang 的 op 大小 = page_size × 每 token KV 字节

`backend_factory.py`：`bytes_per_page = ksize_per_token * page_size`
（`page_first_direct` 布局只算 K；`layer_first` 算 K+V）。Qwen3-0.6B
（28 层、8 KV head、head_dim 128、fp16）每 token K=56 KiB、K+V=112 KiB。

| `--page-size` | page_first_direct(K) | layer_first(K+V) |
|---:|---:|---:|
| 1 | 0.05 MiB/op | 0.11 MiB/op |
| 64 | **3.5 MiB/op** | 7 MiB/op |
| 128 | 7 MiB/op | 14 MiB/op |

实测生产形态：page_size=64 + `page_first_direct`（3.5 MiB/op）写 **83**、
读 **456 MiB/s**；page_size=128 写 **154**、读 **476 MiB/s**。

SGLang hf3fs 官方示例本就是 `--page-size 64 --hicache-mem-layout
page_first_direct`，落在高速档；T5a 探针把 page 硬设成 64 KiB（≈page_size=1
的 layer_first）才是 10.5 MiB/s 的来源——是探针参数失真，不是 SGLang
默认配置的问题。

**Meshy 侧配置建议（不改 SGLang 代码）**：启 hf3fs 后端时用
`--page-size 64 --hicache-mem-layout page_first_direct --hicache-io-backend
direct --hicache-write-policy write_through_selective`，即可把单 op 放到
≥3.5 MiB、写带宽 ≥83 MiB/s，达到目标。不要用 layer_first + 小 page_size。
numjobs 在 rxe 单机上保持 1（json 已设），上物理网卡再调回 16。

### 9.4 权重更新后 L3 会失效吗（正确性，T5c）

**默认不会，是正确性 bug，已在 Meshy 侧修。** 查清 SGLang 0.5.18：

- hf3fs 的 L3 key 是**纯 token 前缀哈希，不含权重版本**。无 cache_salt 时
  `RadixKey.hash_page` 直接对 token 元组求 SHA256
  （`sglang/srt/mem_cache/radix_cache.py:231`；`RadixKey` 注释明确 external
  L3 keys「remain token-only」，cache_salt 只管进程内树）。
- 权重更新 `POST /update_weights_from_disk` 默认 `flush_cache=True`
  （`managers/io_struct.py:1763` 附近），scheduler 回调
  `weight_updater.py:103 flush_cache_after_weight_update → scheduler.py:4251
  flush_cache`，而 `flush_cache` 只做 `tree_cache.reset()`（清 GPU radix +
  host 池引用，`radix_cache.py:353`），**不调 storage 清理**。
- L3 只能由独立端点 `POST /clear_hicache_storage_backend`
  （`entrypoints/http_server.py:1042/1060`）→
  `tree_cache.clear_storage_backend()` → `storage_backend.clear()`
  （`storage_hf3fs.py:535` 清 rank 的 key→page 映射）清掉。
- `release_memory_occupation` 也走同一个 `flush_cache()`（只 reset radix），
  同样不清 L3。

后果：Meshy colocate 下 SGLang server 进程不重启，`Hf3fsLocalMetadataClient`
的 key→page 表是进程内内存并跨 step 存活；训练一步换权重后，同一 prompt 会在
L3 命中**旧策略算的 KV**，rollout 实际策略与记录的 logprob 不一致，污染
GRPO 优势估计。

Meshy 两条权重推送路径都已修：**由 Meshy 自己的配置决定是否调 clear**
（仅当该推理服务 `server_args["hicache_storage_backend"]` 有值时），不依赖
HTTP 状态码——因为 HiCache 未启用时该端点返回的是 **400**（"Hierarchical
cache is not enabled."）而非 404，靠状态码猜会让第一次权重同步直接崩：

- `meshy/engine/sglang.py`：`SGLangEngine(hicache_storage_enabled=...)`，
  `load_weights()` 后仅在启用时调 `clear_hicache_storage()`（托管/colocate
  引擎；标志由 `inference.py` 从 server_args 推导传入）。
- `meshy/engine/titan.py` + `service/topology.py`：非托管副本的 target dict
  带 `hicache_storage_enabled`，`sync_one` 仅对开启 L3 的副本清；配置了却
  清理失败照常 raise。

回归测试 `tests/test_weight_sync.py`（纯 CPU、monkeypatch requests）：
未开 L3 时断言**一次 clear 请求都不发**（`test_load_weights_does_not_touch_l3_when_disabled`、
`test_publisher_skips_l3_clear_when_backend_disabled`）；开了 L3 时断言
update 后必发 clear，且 clear 失败会 raise（删掉修复或误清即失败）。

> 备选方案（未采用）：每权重版本用不同 L3 key 前缀/目录、旧目录异步删除，
> 需要 SGLang 侧按版本命名空间；显式 clear 最简单且语义正确（旧权重 KV
> 在 RL 里本就永不该再被读）。

### 9.5 写策略 / 预取策略与同版本内的 GRPO 收益

写策略（`--hicache-write-policy`，官方 hicache_design）：

- `write_through`：每生成一页立即写 L3，带宽够时命中收益最大，但每次都付 I/O；
- `write_back`：仅在 L2 被驱逐时落 L3，I/O 最省；
- `write_through_selective`：**访问次数超过阈值的热页才写 L3**，只备份热数据，
  省 I/O。

预取策略（`--hicache-storage-prefetch-policy`）：`best_effort`（GPU 能算就
立即停，不等 L3）延迟最低；`wait_complete`（等全部取回）命中最高但延迟最大；
`timeout`（默认，按 token 数设上限）折中，适合有 SLO 的在线服务。

**一句结论（已修正）**：KV 只在**同一权重版本内**有效，所以 L3 的收益**不
包括跨 step 持久化**——每步训练换权重后 L3 必须作废（见 9.4）。在「同一 prompt
采 8 条、GPU radix 已复用 prompt」的 GRPO 里，prompt 段在 L1/L2 已命中、L3
无增量；L3 真实可用收益限于同一 step 内：**多个 rollout 副本共享同一份
generation/draft KV、长多轮 agent rollout 跨请求复用前缀、以及 HBM/L2 放不下
时的容量溢出**。单机 soft-RoCE 带宽有限，配 `write_through_selective`（只落
反复复用的热页）+ 预取 `best_effort`（拿不到就重算，不阻塞）；物理网卡、多
副本后再考虑 `write_through` + `timeout`。

1. **加 zram swap 8 GiB（已在线启用，2026-09-28 23:52，formal run 未中断）。** 不减少 RSS，

   sudo /usr/sbin/swapoff /dev/zram0

### 12.5 空间账：逻辑占用 vs 本地物理实占、回收机制、RF（T5h）

2026-09-30 实测（删除约 36 GB 旧权重后）：

| 口径 | 数值 | 来源 |
|---|---|---|
| 3FS 逻辑总量（meshy） | **51 GB** | `du /3fs/stage/meshy` |
| ├ rollout | 21 GB | 历史 run 的 HF 权重/轨迹 |
| ├ ckpt | 27 GB | clean40b DCP step-10/20（keep2）+ HF |
| └ kvcache | 3.9 GB | HiCache 页 |
| 所有 target UsedSize 求和 | 102 GB | admin_cli list-targets（**RF=2 计两遍**）|
| 本地物理实占 `/data00` | **288 GB / 492 GB（62%）** | df |
| ├ chunk engine s1 | 56 GB | `/opt/3fs/data/s1/engine` |
| └ chunk engine s2 | 56 GB | `/opt/3fs/data/s2/engine` |

#### 为什么删了文件本地盘不释放：两层原因

1. **meta 层延迟 GC（这一层会回收，但要等）。**
   `meta_main.toml [server.meta.gc]`：`enable=true`、`distributed_gc=true`、
   `gc_file_delay='5min'`；storage 层
   `removed_chunk_expiration_time='3day'`、
   `removed_chunk_force_recycled_time='1h'`、`recycle_batch_size=256`。
   即删除后约 5 分钟 meta 标记 chunk 失效，storage 最长 3 天（空间紧张时
   1 小时强制）才把 chunk 归还到**引擎内部空闲表**。无需手动命令；想立即
   触发只能等 GC 扫描（`scan_interval=200ms`）+ 等待上述延迟。

2. **chunk engine 预分配 slab 不 shrink（这一层永不还 OS，是 56GB 的主因）。**
   chunk engine 按 size class 预分配 256 MiB 的 slab 文件
   （`engine/1MiB/00..` 等，非稀疏、`stat` 块数全实占），删除 chunk 只在
   slab 内空闲表标记、供后续写入复用，**不会截断文件或释放磁盘块**。所以
   target `UsedSize`（有效字节，每 target ~3.2 GB）远小于目录 56 GB，差额
   是预分配但当前空闲的 slab 容量。这部分磁盘只有删 data-s1/s2 整个 target
   重建才会归还，运行期无法收缩。

#### 结论与建议

- **不需要、也没有可跑的「立即把空间还给 OS」命令。** 删除后有效容量
  （3FS 可再写）在 GC 延迟后即恢复复用；df 的 `/data00` 数字不会下降，这是
  预分配池的正常行为，不是泄漏。
- 真正缺盘时的手段（按代价排序）：
  1. 删逻辑数据让 GC 回收、供池内复用（df 不降，但可写空间增加）；
  2. 清掉不再需要的 rollout/ckpt 历史目录（当前最大头：rollout 21 GB、
     ckpt 27 GB）；
  3. 要让 df 真正下降，只能停服、删除 `data-s1/s2/engine` 并重建 target
     （数据全失，等于重格式化），或改小 chunk engine 的 slab size class
     配置后重建。
- **RF=2 → RF=1**：两个 target 在同一块 `/data00` 上，无容灾价值，每份写
  两遍。改成 RF=1 只能让**未来写入**占一半、且需要重建 chain table
  （`provision_targets.sh` 改单 target + `upload-chain-table`，需停写窗口），
  已有数据仍按 RF=2 存、需迁移/重写才释放。当前物理盘 62%、逻辑 51 GB，
  尚有余量，不建议为省空间在 MATH run 前动 chain。

| DCP checkpoint | 5.3 GB | step 10/20/30/40 | keep=2，稳态 **10.6 GB**（写新份瞬时 +5.3） |
| in-loop eval | <0.1 GB | 200 题/6 窗 | <1 GB |
| tensorboard | MB 级 | 每步 | <0.5 GB |
| TQ 样本槽 | 内存 | — | 0（不落盘） |

单臂逻辑稳态 ≈ 0.018（traj）+ 3.6（HF 工作）+ 8.4（milestone）+ 10.6（DCP）
+ ~1.5（eval/tb）≈ **24 GB**；DCP 落新份的瞬间约 +5.3 GB。

### 13.3 逻辑 → 物理换算（RF2 + slab 不 shrink）

逻辑写 X → target UsedSize 计 2X（RF=2）；chunk engine 的 256 MiB slab 只增
不减（§12.5），物理峰值 = 运行中同时存活逻辑字节 ×2 取 slab 粒度。

- **单臂**：稳态 ~24 GB 逻辑 ×RF2 ≈ **48 GB 物理**；DCP 写新份瞬态再 +10.6 GB。
- **两臂并存**：若 A 臂清到只剩 milestone（~8.4 GB）再开 B，峰值 ≈
  (24 + 8.4) ×2 ≈ **65 GB 物理**；若两臂都满载并存 ≈ 48×2 ≈ 96 GB。
- 当前 `/data00` df-avail ~191 GB，**任一方式都足够跑完两臂，不会撞盘**，
  且不再依赖轨迹截断的时机。真正约束只剩 DCP 落新份的瞬态与历史 run 清理
  （见 §13.5 起点）。

对比旧（全文轨迹、不 prune）：单臂存活峰值曾估 ~371 GB 逻辑 ×2 ≈ 742 GB，
约第 12-15 窗必撞盘——slim 两层把这个风险消除。

### 13.4 容量看门（挂巡检）

`deploy/3fs-v100/63_storage_watch.py`（只读）：报逻辑总占用 +
rollout/ckpt/kvcache 分项、`/data00` used/avail、当前 run 窗数、按
`XRL_WINDOW_GB` 估的剩余窗数，余量 < 一窗 exit 1。slim 后每窗逻辑增长主要
来自 HF/DCP 的稳态周转而非轨迹，可把 `XRL_WINDOW_GB` 设小（如 0.3）只盯异常
增长；仍建议每窗后跑一次。

### 13.5 跑中保留策略 & T11 启动前清单

保留/删除规则：
- trajectories：slim 默认开，全程留，不删、不重写。
- HF 工作权重：inloop `_prune` keep=3 自动删（确认日志有 `[inloop-prune]`）。
- DCP：`keep_latest_k=2` 自动删旧 step。
- HF milestone + eval 分数表：**留到两臂终评结束**；删任何权重前先报分数表。
- 终评/pass@k 权重：从 milestone 临时复制到 eval 输入目录，用完即删，不同时
  持有多份；最终每臂只留「最佳 1 个 + 最终 1 个」milestone。
- 完成 A 臂终评后，把 A 的工作 HF/DCP 清到只剩 milestone，再开 B 臂。
